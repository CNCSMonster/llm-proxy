# 核心代码定义

## 讨论背景

在测试覆盖率检查中，我们需要明确什么是"核心代码"。不同的定义会导致不同的覆盖率目标和测试策略。

## llm-proxy 的核心价值

llm-proxy 是一个**本地 LLM 协议聚合代理**，核心价值是：

1. **协议聚合** - 将多个上游 provider 聚合到统一端点
2. **协议转换** - 在不同 LLM API 协议间透明转换
3. **零泄露配置** - 为 coding agent 提供安全的配置注入
4. **本地转发** - 为隔离环境提供代理转发服务

## 核心代码的定义标准

核心代码应满足以下条件之一：

### 1. 业务关键路径 (Critical Path)

**定义**: 直接参与核心业务逻辑的代码，如果出错会导致代理无法正常工作。

**包含**:
- `convert.rs` - 协议转换引擎（Chat ↔ Responses ↔ Anthropic）
- `proxy.rs` - 请求路由和转发逻辑
- `config.rs` - 配置解析和验证
- `catalog.rs` - Provider/Model 目录定义

**理由**: 这些是代理的核心功能，任何 bug 都会直接影响用户体验。

### 2. 高频变更代码 (High Churn)

**定义**: 经常需要修改的代码，通常是因为新增 provider/model 或协议支持。

**包含**:
- `catalog.rs` - 新增 provider/model 时需要修改
- `config.rs` - 配置格式变更时需要修改
- `convert.rs` - 新增协议转换时需要修改

**理由**: 高频变更的代码更容易引入 bug，需要更好的测试保护。

### 3. 高风险代码 (High Risk)

**定义**: 出错后影响范围广、修复成本高的代码。

**包含**:
- `auth.rs` - 认证和 token 管理（安全问题）
- `probe.rs` / `probe_coordinator.rs` - 健康检查（影响可用性判断）
- `status.rs` - 状态展示（影响用户决策）

**理由**: 这些代码出错可能导致安全问题或误判系统状态。

### 4. 复用度高的代码 (High Reuse)

**定义**: 被多个模块或路径复用的代码。

**包含**:
- `config.rs` - 被所有模块依赖
- `convert.rs` - 被所有协议路径使用
- `probe_coordinator.rs` - 被 status 和 admin 使用

**理由**: 复用度高的代码出错会影响多个功能。

## 核心代码清单

基于以上标准，llm-proxy 的核心代码包括：

### 第一梯队（必须 80%+ 覆盖率）

| 模块 | 职责 | 理由 | 测试策略 |
|------|------|------|----------|
| `convert.rs` | 协议转换引擎 | 核心业务逻辑，高频变更 | 重点测试转换逻辑 |
| `proxy.rs` | 请求路由和转发 | 核心业务逻辑，高风险 | 重点测试路由和错误处理 |
| `config.rs` | 配置解析和验证 | 被所有模块依赖，高频变更，逻辑稳定 | **90%+**，逻辑固定不易变 |
| `catalog.rs` | Provider/Model 目录 | 高频变更，逻辑简单固定 | **90%+**，CRUD 逻辑简单 |
| `auth.rs` | 认证和 token 管理 | 安全风险，第一梯队 | 重点测试内部逻辑，**不测试外部平台行为** |

**关于 auth.rs 的测试策略**：
- ✅ 测试 token 刷新逻辑、缓存机制、错误处理
- ✅ 测试 OAuth 流程的状态机转换
- ❌ 不测试具体平台（OpenAI/Anthropic/Antigravity）的 API 行为
- ❌ 不测试外部平台的响应格式变化（这些中短期可能变化）

**关于简单稳定模块的测试策略**：
- `config.rs`、`catalog.rs` 等模块逻辑简单且固定
- 应该追求 **90%+** 覆盖率
- 这些模块的测试维护成本低，收益高
- 可以作为"覆盖率缓冲区"，帮助整体达标

### 第二梯队（建议 75%+ 覆盖率）

| 模块 | 职责 | 理由 |
|------|------|------|
| `probe.rs` | 健康检查请求构造 | 影响可用性判断 |
| `probe_coordinator.rs` | 探测协调和缓存 | 影响可用性判断 |
| `status.rs` | 状态展示 | 影响用户决策 |
| `admin.rs` | 管理 API | Server Delegation 架构关键 |

### 第三梯队（建议 60%+ 覆盖率）

| 模块 | 职责 | 理由 |
|------|------|------|
| `admin_client.rs` | 管理客户端 | 辅助功能 |
| `model.rs` | Model 管理 | 辅助功能 |
| `core.rs` | 核心状态管理 | 辅助功能 |
| `service.rs` | 服务管理 | 辅助功能 |

### 非核心代码（不强制覆盖率）

| 模块 | 职责 | 理由 |
|------|------|------|
| `main.rs` | 入口点 | 难以单元测试 |
| `tui/*` | TUI 界面 | 需要集成测试，不适合单元测试 |
| `tui_usage/*` | 使用统计 TUI | 需要集成测试 |
| `clients.rs` | 客户端配置生成 | 辅助功能 |
| `codex.rs` | Codex 特定逻辑 | 客户端特定 |
| `connect.rs` | 连接向导 | 辅助功能 |
| `ownership.rs` | 所有权管理 | 辅助功能 |
| `usage.rs` / `usage_stats.rs` | 使用统计 | 辅助功能 |

## 核心代码覆盖率目标

### 总体目标

- **第一梯队**: 
  - 复杂逻辑模块（convert.rs, proxy.rs, auth.rs）: 80%+ 覆盖率
  - 简单稳定模块（config.rs, catalog.rs）: 90%+ 覆盖率
- **第二梯队**: 75%+ 覆盖率
- **第三梯队**: 60%+ 覆盖率
- **核心代码总计**: 80%+ 覆盖率

### 测试策略原则

1. **外部依赖不测试**
   - 不测试具体平台（OpenAI/Anthropic/Antigravity/DeepSeek 等）的 API 行为
   - 不测试外部平台的响应格式（这些中短期可能变化）
   - 只测试内部逻辑（状态机、缓存、错误处理等）

2. **简单稳定模块高覆盖**
   - 逻辑简单且固定的模块（config.rs, catalog.rs）追求 90%+
   - 这些模块测试维护成本低，可以作为"覆盖率缓冲区"
   - 新增 provider/model 时，测试也应该相应增加

3. **复杂逻辑模块重点覆盖**
   - convert.rs, proxy.rs 等复杂模块追求 80%+
   - 重点测试核心转换逻辑和错误处理路径
   - 边界条件和特殊情况可以适度放宽

4. **新功能必须附带测试**
   - 新增功能必须附带单元测试
   - 旧代码可以逐步补充测试
   - 重构时必须保持或提高覆盖率

## 讨论问题

1. **这个分类是否合理？** 
   - 是否有模块应该升级或降级？
   - 是否有遗漏的关键模块？

2. **覆盖率目标是否合理？**
   - 第一梯队 80% 是否太高或太低？
   - 是否应该对所有核心代码统一要求 80%？

3. **如何平衡测试覆盖率和开发效率？**
   - 是否应该允许某些模块暂时低于目标？
   - 是否应该优先测试新功能而不是旧代码？

4. **如何定义"核心代码"的变更？**
   - 当新增 provider 时，是否需要更新核心代码定义？
   - 当重构某个模块时，是否需要重新评估其分类？

## 建议

1. **保持当前分类**，但定期（每季度）审查一次
2. **优先提升第一梯队**的覆盖率，特别是 auth.rs（安全风险）
3. **简单稳定模块追求 90%+**（config.rs, catalog.rs），作为覆盖率缓冲区
4. **auth.rs 只测试内部逻辑**，不测试外部平台行为
5. **允许渐进式提升**，不要求一次性达到目标
6. **新功能必须附带测试**，旧代码可以逐步补充
7. **admin.rs 需要大量补充**（当前仅 10%），但优先级可以低于 auth.rs
