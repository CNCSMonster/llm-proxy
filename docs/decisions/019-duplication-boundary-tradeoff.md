# ADR-019: 重复代码的边界权衡——DRY 不应跨越独立变化单元

## Status

Accepted

## Date

2026-07-13

## Context

项目开发中经常遇到两段逻辑看起来"一样"要不要合并的争议。DRY 原则本身就要求"同一段知识不应该重复"，但"同一段知识"的边界并不总是清晰的。

本次会话中遇到两个典型案例：

**案例 1：DeepSeek 与 StepFun 的 thinking 启用逻辑**。代码完全一样——都是 `if hasEnable { set thinking } else if reasoningEffort != "" { set thinking } clear reasoningEffort`。代码注释自己写着"与 deepseek 相同的 thinking 启用逻辑"。

**案例 2：协议组合的三张分发表**。forward 路由、error 映射、streaming 路由都按 `(clientType, providerType)` 对做 switch dispatch，case 列表高度重叠。

两个案例都存在"代码一样，该不该合并"的疑问。需要一个判断框架来回答：**哪些重复是真 DRY，哪些是必要的冗余？**

ADR-001（直接协议转换而非统一中间格式）实质上也回答了同一个问题，但当时只针对"协议转换"这个具体场景，没有提炼出更一般的判断原则。

## Decision

采用 **变化单元分析** 作为判断重复代码该不该合并的框架：

**第一步：识别变化单元。** 问"这段代码因为什么样的外部变化而需要修改？"变化单元可以是：平台（DeepSeek、Anthropic）、关注点（路由分发、错误映射、流式处理）、或一个具体的配置值。

**第二步：判断是否跨变化单元。** 如果两段代码服务于不同的变化单元，即使今天看起来一模一样，也不应合并。表面相同的代码只是当前时刻的状态巧合，不是未来不会分岔的保证。

### 判定矩阵

| 场景 | 代码是否相似 | 变化单元 | 应该合并？ |
|------|------------|---------|-----------|
| DeepSeek vs StepFun thinking 逻辑 | 完全相同 | 不同平台（各自独立 API 迭代） | ❌ 不合并 |
| forward / error / streaming 三张 switch 表 | 高度相似 | 不同关注点（路由 vs 错误 vs 流式） | ❌ 不合并 |
| 协议转换 A→B 与 B→A（ADR-001） | 互为镜像 | 不同转换方向（上游 API 各自迭代） | ❌ 不合并 |
| anthropic-version header 7 处硬编码 | 完全相同 | 同一平台的单一配置值 | ✅ 合并为常量 |
| Ollama 三种协议的 TypeEntry | 完全相同 | 同一平台同一模式的机械重复 | ✅ 合并为循环 |

### 证据

代码注释"与 deepseek 相同的 thinking 启用逻辑"恰恰证明了开发者意识到了重复但没有合并——这是一个凭直觉做出的正确判断。变化单元分析为这种直觉提供了可解释的框架。

### 与 ADR-001 的关系

ADR-001 是此原则的第一个应用实例（协议转换路径不应共享中间格式）。本 ADR 将其泛化为一般性原则，并补充了更多案例。

## Alternatives Considered

### A. 严格 DRY——代码相似就应该合并

优点：代码更短。开发体验更一致。

缺点：
- 两个独立平台（DeepSeek / StepFun）的 thinking 逻辑合并后，改一方时必须验证另一方不受影响。这在实践中意味着要么不轻易改，要么引入额外测试来确保不会相互破坏——这两种代价都比保留重复更高。
- 三个不同关注点（forward / error / streaming）的 dispatch 合并后，改动任何一个都需要考虑对整个"协议组合矩阵"的影响，增加认知负担。

拒绝原因：DRY 不应该是目标本身，而是减少维护成本的工具。当合并导致的耦合成本超过重复成本时，保留重复是更优的选择。

### B. 永远不合并——所有重复都保留

优点：最大独立演化空间。

缺点：
- anthropic-version header 7 处硬编码改版本时会漏改，已发生实际 bug（配置验证器漏了 antigravity type）。
- 纯机械重复（Ollama 三份 TypeEntry）不合并只是增加样板代码。

拒绝原因：真正的 DRY 违反（同变化单元的重复）有真实后果。正确的边界不是"从不合并"而是"识别变化单元后决定"。

## Consequences

**收益**：
- 为"该不该合并重复代码"提供了可操作的分析框架，不再凭直觉争论。
- 允许不同平台/关注点独立迭代，不影响彼此。
- 新人理解代码组织时有一致的原则可循。

**代价**：
- 引入了一个新的概念"变化单元"，需要团队理解。
- 变化单元的分析仍有模糊地带，边界案例需要讨论而非机械套用。
- 跨变化单元的重复不会被主动消除，代码总量更高。

**影响**：
- Code review 中遇到重复代码时，reviewer 应问"它们共享同一个变化单元吗？"而不是直接要求消重。
- 测试策略：跨变化单元的重复各自需要独立测试覆盖；同变化单元的重复可共享测试用例。
